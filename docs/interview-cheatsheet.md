# 面試小抄 — ASML CS-OPS Data Analyst

> 對象職缺：ASML Customer Support Operational Excellence — Data Analyst（新竹）
> 專案：Predictive Maintenance → Lean Operations 自動化改善案

---

## 一句話定位

> 我把一個航太引擎預測維護的 AI 模型，**用 Lean（DMAIC）框架落地成一條端到端的營運自動化流程**：模型每天判讀設備健康 → VBA 自動清理 SAP 匯出 → Power Automate 自動歸檔/通知 → Power BI 分層看板監控，並用透明的 ROI 模型驗證效益。

## 2 分鐘自我介紹（扣「兩層浪費」）

「這個專案的起點是一個 NASA 航太引擎的預測維護模型——我用 VAE 把 21 維感測讀數壓成 2 維，再用最近鄰判斷引擎健康，準確率 85%、對『快故障』的召回率 93.9%。

但我發現，真正能幫到維運團隊的，不是模型本身，而是**它周圍的手動作業**。工程師每天要從 SAP 下載資料、在 Excel 手動清理彙整、人工判讀、再手動寄報表——這才是可以被消除的浪費。

所以我用 DMAIC 把它做成一條自動化流程：VBA 巨集把手動 15 分鐘的清理彙總縮到 1.6 秒、Power Automate 讓它無人觸發並自動歸檔、Power BI 做成 Hoshin Kanri 三層看板。最後我用一張假設透明的 ROI 表驗證效益——年省約 539 小時。

整個過程我最在意的是**誠信**：哪些是實測、哪些是假設，我都標得清清楚楚。」

## 兩層浪費（本專案的核心敘事）

| 層 | 浪費 | 解法 | 對應 JD |
|----|------|------|---------|
| **第二層（主角）** 流程浪費：手動 SAP 下載→Excel 彙整→判讀→寄報表 | 人力工時 | VBA + Power Automate + Power BI | *replace manual download from SAP, manual summary in excel, manual sending reports by email* |
| **第一層（亮點）** 實體浪費：設備非計畫停機 | 停機成本 | VAE 預測維護模型 | *proactive and predictive data model to act before issue happen* |

> 主從關係：**流程自動化是主角，AI 模型是它自動化處理的判讀引擎。**

## JD 六大關鍵字 × STAR 小故事

### 1. VBA
- **S**：SAP 匯出檔有髒資料（前後空白、大小寫不一、三種日期格式、千分位、重複列），工程師每天手動清。
- **T**：把手動清理彙總自動化。
- **A**：寫 VBA 巨集自動去重、TRIM、統一大小寫與日期、轉數值，並依機台彙總警告數；內建 Timer 記錄耗時。
- **R**：13,096 列處理從 **15 分鐘 → 1.6 秒（約 562×）**，且消除人工漏 TRIM 造成的靜默錯誤。

### 2. Power Automate（RPA）
- **S**：巨集還是要人手動開檔、觸發、寄送。
- **T**：做成無人流程。
- **A**：Power Automate Desktop 流程自動取檔→開 Excel→跑無對話框巨集（我特地寫了 `CleanAndSummarizeSilent` 避免彈窗卡住 RPA）→歸檔→通知。
- **R**：端到端無人化，可掛 Windows 排程每日自動跑。

### 3. Power BI（HK BI）
- **S**：報表是靜態 Excel，主管看不到全局趨勢。
- **T**：做可監控的儀表板。
- **A**：Power BI Hoshin Kanri 三層看板——Tier1 高層 KPI、Tier2 部門趨勢與潛空間散佈圖、Tier3 現場明細；用 DAX 量值、條件式色階。
- **R**：一眼看出 86/100 台有警告、警告隨時間遞增（156→286→1,251）、哪些機台最急。

### 4. Power Apps
- **S**：現場人員需要即時查詢單台健康，不用回辦公室。
- **T**：設計現場 App。
- **A**：設計三畫面（機隊總覽/單台明細/即時查詢）線框圖與規格，串接 VAE 推論的整合架構。
- **R**：（誠實說明）因個人帳號無 tenant，止於設計稿；在 ASML 環境可用 Dataverse + 自訂連接器實作。

### 5. Lean / LSS（DMAIC）
- **A**：用 DMAIC 定義流程浪費、量測基線、以 TIMWOODS 分析根因、對應工具改善、以看板控制。
- **R**：把一個 AI 專案重構成可被營運團隊採用的精實改善案。

### 6. ROI / Benefit Validation
- **A**：做一張 Excel ROI 模型，實測值（綠）與假設值（黃）分色，ROI 全用公式。
- **R**：年省約 539 小時 / 約 NT$27 萬、回收期 < 3 週；**假設可當場替換成 ASML 真實數字立即重算**——這正是 benefit validator 該有的嚴謹。

## 可能被問的技術/情境題

**Q：資料是真的還是假的？**
> 感測讀數、引擎編號、模型判讀都是**真實** NASA CMAPSS + 我的 VAE 跑出來的；只有工單號、維護成本、匯出日期是模擬（因為那是 SAP 側欄位，資料集沒有）。我在 README 有完整的真實/模擬對照表。

**Q：為什麼一開始異常數每台都一樣？（若被追問資料細節）**
> 我一開始用訓練集，每台都跑到故障，所以固定 31 筆異常——那是被定義決定的常數，不是資料的事實。我改用測試集（故障前隨機截斷 = 當前艦隊快照），異常才有鑑別度：75 台健康、25 台不同程度警告。這是我對資料語意的敏感度。

**Q：效益數字可信嗎？**
> 分兩種：15 分鐘→1.6 秒是碼錶+程式**實測**；年省工時是**假設推算**（每天 3 次×3 人×240 天），我在 ROI 表用顏色分開、假設可改。我不會把假設講成實測。

**Q：模型怎麼判讀？**
> VAE encoder 把讀數壓成 2 維 embedding，找最近的 support 樣本、取其標籤（1-NN），不是設距離門檻。準確率 85%、對快故障召回 93.9%、只漏判 2 台——偏向寧可誤報不漏判，符合維運實務。
